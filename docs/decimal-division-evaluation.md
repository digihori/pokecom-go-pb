# 除算の切り分けと補完候補の評価

実施日: 2026-11-03

## 判断

数値試作は、**bignumの整数・十進表現と加減乗算を利用し、除算だけを正確な商・余りで補完する構成**で、次の共通基盤評価へ進める。これは試作を進めるための条件付き判断であり、製品の数値ライブラリやPB丸め仕様の本採用ではない。

元のライブラリ除算をそのまま採用する案と、固定のガード桁を増やすだけの案は採用しない。ライブラリのフォークや多倍長整数演算の自作は行わず、既存BigIntegerの商・余りを使う小さな評価用アダプタを作った。

## 元の除算が不一致となる理由

bignum 0.3.10の有限精度`divide`は整数化した値を除算し、商と余りを`roundDiscarded`へ渡している。商から追加の桁を落とさない経路では、`determineDecider`が余りの先頭桁を使って丸めを判断する。ここで必要な「余りの分母に対する比率」が反映されない。

`2/3`の12桁指定を追うと、整数化した`2×10^12`を`3`で割り、商は`666666666666`、余りは`2`となる。正しい半端の判定は`2×余り >= 分母`、すなわち`4 >= 3`なので切り上げる。一方、余りの先頭桁`2`を基準にすると切り上げられない。この経路の不一致を説明できる。

[評価した版のdivide・roundDiscarded・determineDecider](https://github.com/ionspin/kotlin-multiplatform-bignum/blob/0.3.10/bignum/src/commonMain/kotlin/com/ionspin/kotlin/bignum/decimal/BigDecimal.kt)を確認した。ライブラリ全体の全不具合を網羅した調査ではなく、上流への修正提案・Issue投稿も行っていない。

## ガード桁方式の反例

前回の「24桁で除算してから12桁へ丸める」診断は、限られた比較では一致した。しかし次の値を1で割るケースでは、直接12桁へ丸める結果と一致しないことをJVM・iOSで再現した。

`1.2345678901249999999999999 / 1`

直接12桁のHALF_UPで丸めた正解は`1.23456789012`。途中の丸めで境界値へ移動してからもう一度丸めると、結果が変わり得る。ガード桁を固定数増やすだけでは、入力桁数が広がった場合の一般解にはならない。

## 除算補完の方法

1. 十進値を整数係数と10の指数へ分解し、符号を分ける。
2. 係数の桁数と整数比較で商の指数を求める。Doubleや対数は使わない。
3. 指定の有効桁数に合わせて分子または分母を10の整数べきで調整する。
4. BigIntegerの除算で整数商と余りを一度求める。
5. `2×余り`と分母を比較し、HALF_UP／HALF_EVEN／DOWNの指定に従って丸める。
6. 符号と指数を戻して十進値を作る。中間の近似除算・二重丸めは行わない。

丸め方は比較用の3方式であり、PBがこのいずれを使うかを確定していない。試作の制限は入力文字列300文字、係数256桁、解析後指数±1000、有効桁数1〜100。これらをPBの入力上限や互換仕様へ転用しない。

| 独立したPython decimalの1,000組×3丸め方式（3,000比較） | 全一致 | 全一致 |

独立参照の除算入力は係数1〜30桁・入力指数±99、有効桁数1／2／10／12／24を含む。同じ埋め込みベクトルを両ターゲットで使用した。一般化のための数学的検討と境界試験は行ったが、全入力を尽くした検証ではない。

候補を選んだ実行コマンドは成功終了した。従来の生ライブラリ除算を検査する失敗試験はそのまま残し、通常の全件試験を成功したようには扱わない。今回の選択実行はJVM 7メソッド、iOS 6メソッドで失敗0件。[実行ログ](../prototypes/foundation/results/division-candidate-gradle.log)、[結果要約](../prototypes/foundation/results/division-candidate-summary.json)

なお、Releaseはリンク確認のみで、実機・Release実行は未実施。試験時間の記録はあるが、停止応答やメモリの性能評価を完了したものではない。

## 今回の判断と残課題

- 共有Kotlinによる数値基盤を継続する。除算候補をPBNumber相当の境界へ閉じ込める構成で、最小セッションとLCDの評価へ進める。
- `DecimalProbe`は元の挙動、`ExactDivisionProbe`は補完候補、`CandidateArithmeticProbe`は両者を組み合わせた比較用経路として分離する。
- 数学関数は未評価。非整数べき、平方根、対数・三角関数の方式と精度は別途決める。今回の除算補完だけで全BASIC数値計算がそろうとはしない。
- PBの丸め方式・時点、演算の中間精度、数値範囲・エラー・表示は資料／実機確認待ち。実機互換の合格を宣言しない。
- 係数桁数と指数の製品上限、処理時間・メモリ、Androidと主要デスクトップでの実行は引き続き評価する。

本結果は[初回評価](foundation-evaluation-results.md)の「数値候補をそのまま採用しない」という判断を維持し、補完した候補で試作を進められるところまで具体化したもの。
