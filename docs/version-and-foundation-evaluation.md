# バージョン構成と数値・iOS共通基盤の評価計画

作成日・公式資料確認日: 2026-11-03

実施状況更新: 技術試作に着手。[初回評価結果](foundation-evaluation-results.md)にJVM／iOSの実測結果と数値候補の問題を記録した。以下の「未実施」は計画作成時点の状態を示す。

## 位置付け

主要5OSに向けたKMP＋Composeの採用方針を、評価用の具体構成へ落とす。本書の版は**評価開始候補**であり、ビルド成功・数値互換性・製品の最低OS版が確定したことを意味しない。今回は文書化までとし、依存導入、評価コード作成、ビルド、端末試験は実施していない。

評価の出口は「共有BASIC基盤をこの構成で進められるか」「数値候補を採用できるか」「実機仕様の追加確認は何か」の3点とする。デスクトップ先行を維持し、iOSの完成版Playerを先に作る計画にはしない。

KMP 2.4.20–2.4.21の互換表はGradle 7.6.3–9.7.0、AGP 8.5.2–9.3.1、Xcode 26.4を掲載している。AGP 9.3はGradle 9.5.0以上を要求するため、その共通範囲を採る。AGPだけを最新版へ上げない。[KMP互換表](https://kotlinlang.org/docs/multiplatform/multiplatform-compatibility-guide.html)、[AGP 9.3互換条件](https://developer.android.com/build/releases/agp-9-3-0-release-notes)

Compose CompilerはKotlinと同じ版を使う。Android側のCompose依存はCompose Multiplatformの対応に従い、別のBOMで無条件に上書きしない。[Compose互換性](https://kotlinlang.org/docs/multiplatform/compose-compatibility-and-versioning.html)

共通Androidライブラリは`com.android.kotlin.multiplatform.library`を使用する設計とし、Androidアプリのモジュールを分ける。旧`androidTarget`構成を新規設計の基準にしない。AGP組込みKotlinとのプラグイン重複も初期構成で確認する。[KMP移行指針](https://kotlinlang.org/docs/multiplatform/multiplatform-compatibility-guide.html)

Coroutines 1.11.0はKotlin 2.2.20、Serialization 1.12.0はKotlin 2.4.10を基盤とするリリース。これだけで本構成の全ターゲット動作を保証せず、依存解決・リンクを評価する。[Coroutinesリリース](https://github.com/Kotlin/kotlinx.coroutines/releases/tag/1.11.0)、[Serializationリリース](https://github.com/Kotlin/kotlinx.serialization/releases/tag/v1.12.0)、[bignumリリース](https://github.com/ionspin/kotlin-multiplatform-bignum/releases/tag/0.3.10)

### 対象OS・CPUの扱い

初期評価点はWindows 10以降x64、macOS 13以降Apple Silicon、Ubuntu 22.04 x64、Android arm64＋エミュレータx64、iOS arm64＋Simulator arm64とする。Windows/Linuxのarm64は後続の配布確認対象とする。OSの最低版で実際に動かしていなければ、上位OSでの成功から最低版対応を認定しない。

Compose 1.12.2の公式表にはmacOS 13 arm64が記載されている。**Intel Mac対応はこの構成の保証対象に含めず未決とする**。必要なら、公式対応範囲と配布ランタイムを再調査し、構成を見直す。Windows CE・Brainuxを今回の合否条件にしない。[公式プラットフォーム表](https://kotlinlang.org/docs/multiplatform/compose-compatibility-and-versioning.html)

### 手元環境と差分

読み取りで確認した手元環境はApple Silicon（arm64）、Xcode 26.6（17F113）、JBR 21.0.11。Xcode 26.6は公式互換表の26.4と一致しない。まず手元環境で依存解決・Nativeリンクを確認し、失敗した場合は26.4の並行環境で再現を分ける計画とする。現時点でXcodeの追加・切替・ダウングレードは行わない。26.6で成功しても公式サポート範囲が変わったとは記録しない。

版は将来のversion catalogとWrapperに完全固定し、動的版を使わない。各評価結果に依存一覧・ツール版・OS・CPU・ビルド種別を添付する。QR、MCP、カメラ等の版固定は各機能の着手時とし、今回の最小評価へ加えない。

## 2. 数値計算の評価

### 評価する境界

PBNumberの内側に数値ライブラリを閉じ込め、文字列から値を生成する。通常演算・保存・比較の経路でDoubleを介さない。直接入力とプログラム実行は同じ演算経路を使う設計を確認する。

内部仮数部12桁、LCD 12文字、数値表示の仮数桁数は分離する。マニュアル転記にある最大値`9.999999999E99`を、内部12桁を理由に`9.99999999999E99`へ変更しない。[マニュアル仕様記録](references/manual-specifications.md)

次の3段階で判定する。

1. **十進ライブラリの適合**：指定精度・丸め・指数で期待どおり動き、JVMとNativeで一致するか。
2. **PB数値モデルの適合**：丸め方式・丸め時点・範囲判定等を実機／資料と照合できるか。
3. **PB表示の適合**：内部値を保持したまま、符号・指数・桁数・ゼロ表示が一致するか。

1の成功だけでPB互換を認定しない。旧版との一致も実機互換とは別の比較結果として残す。

### 試験ケースと期待値の根拠

| ID | 入力・観点 | 判定方法 |
| --- | --- | --- |
| N01 | `0.1+0.2`、`1.2*3.4`、負数・ゼロ | それぞれ0.3、4.08。二進浮動小数の残差が混入しない |
| N02 | 同値の`1`、`1.0`、指数表記、大小比較、負のゼロ | 数値の同値性と表示規則を分け、同値を誤判定しない |
| N03 | `1/3`、`2/3`、`1/7`、循環小数の連鎖 | 有限精度で必ず終了。明示した丸め規則と独立参照値に一致 |
| N04 | 12桁境界、桁上がり、正負の中間値 | `1.234567890125`等でHALF_UPとHALF_EVENを識別。PBの採用規則は未決 |
| N05 | `(1E12+1)-1E12`、相殺、乗除の連鎖 | 演算ごと12桁なら0、高精度保持なら1となるモデル差を観察。PBの答えは実機確認前に確定しない |
| N06 | ±`1E-99`、±`9.999999999E99`、0、その上下 | 入力・中間演算・代入・表示での範囲判定時点を分ける。範囲外のゼロ化／エラーは資料・実機で確認 |
| N07 | ゼロ除算、負数の平方根、対数の定義域、負数の非整数べき | ホスト例外・NaN等を漏らさずPB診断へ変換。エラー番号は根拠確認後に固定 |
| N08 | 整数べき、平方根、対数・指数、三角関数、角度単位 | 関数の提供範囲と精度を棚卸し。既知値と独立した高精度参照値で比較 |
| N09 | 正負・通常／指数表示の切替境界、表示丸めで桁上がり | マニュアルの表示桁数に従う。表示処理で内部値を丸め直さない |
| N10 | 十進文字列→JSON→復元、同じ入力列の再実行 | 値・診断・表示が一致。Double経由の変換を検出 |
| N11 | 同じ式を直接入力・代入・連続実行・命令単位実行 | 結果・内部値・診断に差がない（この項目は最小インタープリタ導入後） |

まずN01–N10の手作業で期待値を確認した固定ケースを50件以上用意し、ライブラリ評価では固定seedの生成ケース1,000件以上を追加する。件数を満たすだけで合格にせず、各境界分類が含まれることを確認する。

期待値の出典を「数学的に厳密」「明示した候補丸めモデル」「マニュアル」「実機観測」「旧版観測」に分ける。全ターゲットで同じライブラリが同じ誤答を返す可能性があるため、ターゲット間一致だけを正解の根拠にしない。四則演算の独立参照には評価専用のJava BigDecimal等を使い、数学関数の高精度参照手段は関数方式の選定とともに固定する。

丸め方式・タイミングが不明なケースは「未確定」とし、都合のよい値を期待値へ採用しない。内部計算のガード桁数、三角関数等のアルゴリズムと許容誤差も未決。関数の誤差を一律の絶対値許容だけで処理しない。

### 数値候補の合格条件と代替

- JVM、Android、iOS Simulator／実機で共通の入力ベクトルを使い、確定期待値の不一致0件、未処理例外0件。
- 分母・精度・丸めを明示でき、循環小数、指数境界、負数で停止不能にならない。
- Native DebugだけでなくReleaseでも同じ数値結果。利用するAPIとライセンス・保守状態を記録する。
- 四則演算の採用可否と数学関数の採用可否を分ける。bignumに必要な関数がそろっていると仮定しない。
- 数値プリミティブ単体で時間・メモリを測る。高精度演算1回が長時間戻らない場合、命令間のyieldだけでは停止応答を保証できないため、演算の入力制限／方式を見直す。

不適合時は、まずアダプタの指定誤りとライブラリの制約を切り分ける。必要なら共通Kotlinの別候補、または限定したネイティブ数値接続を比較する。Doubleへの無条件置換や、全面自作の多倍長演算へ直行しない。

## 3. iOS共通基盤の評価

完成版の画面やBASIC全文法は作らず、数値・セッション・LCDの小さな経路を確認する。試作を開始する際は製品コードと評価用コードの境界を明示する。

| ID | 評価項目 | 合格条件・残す証拠 |
| --- | --- | --- |
| I01 | UIなし共通数値コードと依存解決 | JVM、iosSimulatorArm64、iosArm64のコンパイル・リンク成功。旧Kotlinで作られたbignumのKLIBも確認 |
| I02 | Simulatorで共通試験を実行 | N01–N10の確定ケースがJVMと一致。ビルド成功だけで実行成功にしない |
| I03 | Composeとの最小接続 | 固定キャラの12セルLCD、値、実行状態、操作ボタンが表示・更新できる。任意グラフィック機能は追加しない |
| I04 | セッション所有・非同期処理 | 実行処理がUIを占有せず、同時操作でも状態の書換え主体が1つ。待機中も停止・終了を受け付ける |
| I05 | INPUT待ち・表示待ちの模擬状態、停止、再購読 | 要求ID・状態版・操作結果が欠落／二重処理されず、再表示時にも待機状態が分かる |
| I06 | バックグラウンド／復帰、画面破棄・再生成 | セッション二重起動・クラッシュ・勝手な入力確定なし。復帰後に同じ状態を取得できる |
| I07 | 小さなJSONとBASICエスケープ文字列の往復 | 数値精度と特殊記号が維持される。カメラ・ファイル権限の製品実装は別評価 |
| I08 | iOS実機のDebug／Release実行 | arm64実機で数値・操作が一致し、最適化時だけの異常がない。署名・リンク条件も記録 |
| I09 | 応答時間・メモリ | 連続演算中の停止要求を暫定目標100ms以内で反映。計測条件と最大値を記録。起動・反復操作後のメモリ増加も観察 |

100msは評価用の暫定目標で、実機BASIC速度の再現値ではない。実行速度調整で低速にしても、操作応答を同じ待ち時間で遅延させない。重い数値演算とUI描画を分けて測る。

I06はまずバックグラウンドへ入ると実行を保留する評価用ポリシーで確認する。製品として自動再開するかは別途決める。アプリ強制終了後の実行状態復元やタイムトラベル機能は今回の合格条件に含めない。

実機未確保・署名不可の場合はI08を未実施とし、SimulatorだけでiOS採用評価を完了にしない。最低iOS版の実機／Simulatorが用意できない場合も、その版の保証は残課題とする。

## 4. 実施順序と判定

| 段階 | 作業 | 次へ進む条件 |
| --- | --- | --- |
| E0 | 版・依存・OS／CPUの記録、Xcode差分の確認 | 対象構成と失敗の再現条件を説明できる |
| E1 | I01、最小の十進演算のリンク・実行 | Native依存を利用できる。失敗時はUIを増やさず原因を分離 |
| E2 | N01–N10、I02、数値API／数学関数の棚卸し | 四則演算候補の採否と、実機確認待ちの仕様が分かれる |
| E3 | I03–I07、セッション・LCD接続 | 所有・待機・状態通知・画面復帰が成立 |
| E4 | I08–I09、Android共通試験、主要デスクトップでUIなし試験 | 実機Releaseと主要ランタイムで共通処理の差異を確認 |
| E5 | 評価報告と版固定の更新 | 採用／条件付き採用／不採用を項目別に決定し、基本設計へ反映 |

数値・セッション共通試験はmacOS JVMだけでなく、Windows/Linux JVMでも実施する。各OSのパッケージ作成・インストール確認は後続の配布評価で行う。全5OSの配布保証と今回の共通基盤評価を混同しない。

最初にNative依存とXcodeの問題を発見し、その後に数値モデルとUI接続へ進む。iOS上で構造的に共通化できない問題が出た場合も、Core、セッション、Compose、OS接続のどこで起きたかを分けて技術選定を再検討する。

## 5. 記録する成果物・未決事項

評価時に次を残す計画とする（現時点では未作成）。

- 環境／依存版一覧と再現手順、ビルド・リンクログ。
- 入力ベクトル：ID、入力、精度モデル、期待値、出典、ターゲット別結果。
- 数値APIの対応表：四則、比較、丸め、べき、数学関数、未提供機能。
- 応答・性能結果：端末、OS、Debug／Release、負荷、試行回数、時間、メモリ。
- 評価報告：採用条件、失敗と回避策、未実施項目、互換仕様の未決一覧。

仕様確定に必要な資料は、マニュアルの機種・版・ページ、数値計算／エラー／表示の該当ページ、実機でN04–N09を確認した入力と表示記録。旧版は比較対象にし、正解の唯一の根拠にしない。最初の評価前に全資料を要求せず、数値ライブラリ評価と並行して不明な丸め・範囲規則を確認する。

未決事項はPBの丸め規則・中間精度、数学関数方式、製品の最低OS版とIntel Mac対応、Xcode 26.6の実動作、iOS実機の調達／署名条件。**評価結果はすべて未実施**。本書の作成によって初回リリース範囲を増やさない。
